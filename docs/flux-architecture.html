Component lanes — what each tier actually does

Dev and release render through the same declarative components (AGENTS.md §0.2): the shadow tree is not a tree of native views; each ShadowNode holds materialized props in a platform observable and the same component vocabulary is fed by the VM (dev) or by codegen (release).

Dev Server (Rust)

  • flux-cli dev → flux-devserver Pipeline
  • parse → type_check → lower → diff → frame
  • Retains last_good tree; ships Init/Delta/Unchanged
  • dispatch.rs DependencyIndex (ADR-0027): on write to S, re-sends only dependents[S]
  • wrote signal nobody reads → ships nothing (noop budget)
  • handler section = shared bytecode blob + ClosureRefs (Gap G1)

Native Runtime (iOS≈Android)

  • Transport → FrameDeserializer (mirrors Rust serializer)
  • Executor.apply seeds signals + string table, registers handlers
  • Handler bytecode decoded once & cached → reused per tap (R3)
  • dispatch: VM runs closure, folds written signals into graph
  • reconcileDirty walks only subtrees reading written signals (R1)
  • @pure nodes with unchanged prop hash skipped (G6)
  • Adapters mutate native views in place by stable NodeId

Shared Model & Parity

  • VMValue tag set 0x00–0x07 is the wire contract (Swift/Kotlin/Rust)
  • flux-vm-ref is the oracle; both native VMs conform via ISA vectors
  • flux build → idiomatic SwiftUI / Compose from same LoweredIr
  • flux-parity reduces dev-VM trace + both codegen outputs to one ViewNode
  • Empty ForEach splice faithful on all 3 paths (FLUX-014)
  • Node IDs via compute_node_id with correct tag family (§3.2)
